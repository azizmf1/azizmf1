### Purpose

During implementation planning against BRS v1.0, a number of requirements were found to be undefined, incomplete, or internally inconsistent. This RFI requests formal answers so that implementation is not based on assumption. Where an interim assumption has been adopted to avoid stopping delivery, it is stated explicitly below and should be either confirmed or corrected.

---

## Item 1 — Integration with the Ministry of Environment, Water and Agriculture (MEWA)

**BRS reference:** Solution Scope item 2; UC04; MSG17; MSG18.

**Issue:** Sharing the approved medical report with MEWA is listed in the solution scope and is stated to the user in the approval confirmation messages, but the BRS contains no use case, no interface specification, and no error handling for it.

**Information required:**
1. The integration interface specification: endpoint(s), protocol, authentication method, and environments (staging / production).
2. The exact payload — which fields of the medical report are shared, in which format.
3. The trigger point — is the report dispatched at the moment of approval, in batch, or on request by MEWA?
4. Are **Not Fit** reports shared, or only **Fit** reports? Both confirmation messages (MSG17 and MSG18) state that the report will be shared, which implies both — please confirm.
5. Failure handling — if dispatch fails, does the report still reach `Completed`? What is the retry policy, and is there any operational visibility or manual re-dispatch requirement?
6. Does MEWA return an acknowledgement or a reference number that must be stored or displayed?
7. Is there any requirement to notify MEWA when a `Completed` report subsequently becomes `Expired`?

**Interim position:** Approval is being implemented so that it completes independently of dispatch, with the dispatch intent persisted for later delivery. No integration is being built until this item is answered.

## Item 2 — Applicant registry integration

**BRS reference:** UC02 Basic Flow step 3; MSG04.

**Issue:** The BRS states that the system validates applicant information "from Registry" but does not name the system, define the interface, or specify the field mapping.

**Information required:**
1. Which registry is used, and its interface specification and environments.
2. The exact request parameters. Assumed: ID Type, ID Number, Date of Birth.
3. The exact response fields. Assumed: Full Name (Arabic), Full Name (English), Nationality, Gender.
4. What happens when the applicant is **not found** — is manual entry permitted, or is report creation blocked?
5. Are there cases where the registry returns a partial record (for example, no English name)?

**Interim assumption adopted:** the request and response fields listed above, with `MSG04` displayed on failure or not-found.

## Item 3 — Field editability condition

**BRS reference:** Logical Data Model, UC02 / UC03 / UC06 — the `Y/N` value in the "Editable?" column for Full Name (Arabic), Full Name (English), Nationality and Gender.

**Issue:** These four fields are marked `Y/N`, which indicates a conditional rule, but the condition is not stated anywhere in the BRS.

**Information required:** the exact condition that determines whether these fields are editable.

**Interim assumption adopted:** a field returned by the registry is read-only; a field the registry does not return is editable by the Data Entry user. ID Type, ID Number and Date of Birth are never editable after the registry lookup.

## Item 4 — ID number length and format per ID type

**BRS reference:** UC01 search field and list column (`Length = 20`, note: "If the id type is GCC, system shall accept 20 characters"); UC02 Logical Data Model (`ID Number`, no length stated).

**Issue:** No length or format validation is defined per ID type on the report form, and the only stated constraint (20) appears solely on the list and search screens.

**Information required:** the validation rule for each ID type — Citizen, Resident, and GCC.

**Interim assumption adopted:** Citizen = exactly 10 digits beginning with `1`; Resident = exactly 10 digits beginning with `2`; GCC = up to 20 alphanumeric characters.

## Item 5 — Nationality lookup values

**BRS reference:** Lookups — Nationality.

**Issue:** The nationality lookup table in the BRS is present but contains no values.

**Information required:** either the authoritative value list (Arabic and English), or confirmation that the list is served by an existing Seha lookup service — in which case, the service reference and the code scheme used.

**Interim assumption adopted:** the list is retrieved from the Seha lookup service and is searchable, per the BRS note on the field.

## Item 6 — Duplicate report rule: incomplete business rule and uncovered case

**BRS reference:** UC02 — BR01, BR02, BR03, BR08.

**Issue A — incomplete rule.** BR03 reads: *"An applicant is allowed to have another medical report ONLY IF exist one is either expired"*. The sentence is incomplete; the alternative following "either" is missing.

**Issue B — uncovered case.** BR02 exempts an applicant when an existing report has a **Not Fit** result. BR08 states that when a new report is created, the existing **Not Fit** report is set to `Expired`. Neither rule addresses a **Not Fit** report that has **not yet been approved** — that is, one still in `Pending for Auditing`, `Draft`, or `Requires Modification`.

**Information required:**
1. The complete text of BR03.
2. Confirmation of the consolidated rule: *an applicant shall not have more than one valid or in-progress medical report, unless the existing report is Expired or its result is Not Fit.*
3. Whether the **Not Fit** exemption applies only once the Not-Fit result has been **approved** (status `Completed` or `Expired`), or also to an unapproved Not-Fit report still under auditing.
4. Confirmation that "in progress" comprises `Draft`, `Pending for Auditing` and `Requires Modification`.

**Interim assumption adopted:** the Not-Fit exemption applies only to an **approved** Not-Fit result; an unapproved Not-Fit report still blocks creation of a new report.

## Item 7 — Vision level lookups

**BRS reference:** UC02 Logical Data Model — fields referencing "Lookups: Levels of Eye vision" and "Lookups: Levels of Eye vision with correction"; Lookups — Vision.

**Issue:** Two distinct lookups are referenced by the form fields, but only one lookup ("Vision": 1–6 and *No Vision*) is defined in the BRS.

**Information required:** confirmation that both the uncorrected and the corrected vision level fields draw on the same value list, or the second value list if they differ.

**Interim assumption adopted:** both fields use the single defined list.

## Item 8 — Source of medical facility and city data

**BRS reference:** UC02 / UC03 Logical Data Model — `Medical Facility Name` and `City`, noted as "Retrieved from SEHA"; UC01 search fields and list columns.

**Information required:**
1. Confirmation that on the report form these two values are derived from the authenticated user's own medical center and are never selectable.
2. The Seha service reference used to populate the City and Medical Center Name dropdowns shown to the System Admin on UC01, and the code scheme used.
3. On UC05 the admin-only block additionally shows `Medical Org. Type` and `Region` — please confirm the source for these two.

## Item 9 — Minor documentation corrections (for the record)

The following were resolved by Business Analysis as evident transcription issues and are noted here for confirmation only; they are **not** blocking.

| Ref | Issue | Resolution applied |
|---|---|---|
| Use case numbering | Body and table of contents number Submit as UC02 and Save as Draft as UC03, but several cross-references point to "UC03: Submit Medical Report" and others read "UC00". | Body and table of contents treated as authoritative: UC01 List, UC02 Submit, UC03 Save as Draft, UC04 Audit, UC05 View, UC06 Edit, UC07 Export. |
| Message IDs | UC01 references MSG001 and MSG002; the message catalogue defines MSG01 and MSG02. A row reading "Notification's: MSG01" also appears at the foot of every use case. | Catalogue treated as authoritative; the repeated footer row treated as a template artifact. |
| List sort | Stated as "sorted from earliest to oldest based on last update date", which is self-contradictory. | Implemented as descending by last update date (most recently updated first). |
| `سلامة الجسم / Body Health` | The "Type" cell is empty in every Logical Data Model table in which the field appears. | Implemented as a Radio Button (`سليم / Passed`, `غير سليم / Failed`), matching `سلامة العقل / Mental Health` in the same section. |
| UC04 post-condition | The Post-Condition row is empty. | Taken from the basic flow: status becomes `Completed` and an action log entry is written. |
| "Print" vs "Export" | UC01 offers a `طباعة / Print` action while UC05 offers `طباعة / Export` pointing to UC07. | Treated as the same action (PDF export per UC07), and therefore available only for `Completed` reports. |
| System Admin capability | Admin appears as an actor on UC01 and UC05 only. | Implemented as read-only within this module. |
| Expired reports | The BRS does not state whether an expired report may be viewed or exported. | Viewable; not exportable (UC07 requires `Completed`), not editable, not auditable. |
| Service Process Flow | The section is present but contains no diagram. | The state machine derived from the use cases is treated as complete. |

Please confirm these resolutions, or advise where the intent differs.
